# GUI 上传原生 Rust 化（与下载对称）

## 目标
把 GUI 上传从 zmodem.js+IPC 路径改为原生 Rust（`zmodem_tx.rs`），和下载路径对称，目标速度 ~7-10MB/s（当前 1.6MB/s，Xshell 10MB/s）。

## 背景
- 下载已走原生 `ZmodemReceiver`，7MB/s，数据不过 IPC
- 上传仍走 zmodem.js（JS 编码+IPC），优化到极限也才 1.6MB/s
- `ZmodemSender` 已完整实现并在 MCP 中验证可用
- 前端已监听所有需要的事件（progress/file_complete/end/error）

## 改动清单

### 1. ssh.rs — reader loop 集成原生发送器

**新增字段**（`channel_reader` 内）：
- `zmodem_tx: Option<ZmodemSender>` — 对称于 `zmodem_rx`
- `tx_queue: VecDeque<UploadFile>` — 多文件队列，每项含 `{path, name, size, mtime}`

**新增 SessionCommand**：
- `ZmodemStartUpload { paths: Vec<String> }` — 对称于 `ZmodemAcceptOffer`

**handle_incoming_data 改动**：
- upload passthrough 分支：检测到 ZRINIT 时仍 emit `zmodem_start(upload)`，但不再 emit `zmodem_raw`（Rust 自己处理）。设 `mode=Zmodem`，`zmodem_tx=None`（等前端调 start_upload 后才有 sender）。**保留旧 passthrough 作为 fallback**：如果收到 ZRINIT 后一定时间内没收到 start_upload 命令，退回 passthrough。
- Zmodem 模式下 `zmodem_tx` 为 Some 时：`sender.feed(&data)` → `dispatch_tx_actions` → `channel.data(actions.send)` → `poll(&mut file)` 循环发数据。完全镜像下载的 `rx.feed` → `dispatch_rx_actions` → `channel.data` 模式。
- ZEOF 后收到 ZRINIT（下一个文件）：从 `tx_queue` 取下一个文件创建新 sender；队列空则发 ZFIN。

**新增 `dispatch_tx_actions`**：镜像 `dispatch_rx_actions`，把 `TxEvent` 翻译成已有的 Tauri 事件（`zmodem_progress`/`zmodem_file_complete`/`zmodem_end`/`zmodem_error`），payload 格式完全一致，前端无需改。

**新增 `ZmodemStartUpload` 命令处理**（select 的 command 分支）：打开文件列表第一个，创建 `ZmodemSender::new(name, size, mtime)`，存入 `zmodem_tx`，剩余文件存入 `tx_queue`。如果此时已有缓存的 ZRINIT 字节，立即 feed。

### 2. main.rs — 新增 Tauri 命令
- `zmodem_start_upload(session_id, paths: Vec<String>)` — 薄包装，发 `SessionCommand::ZmodemStartUpload`，注册到 `invoke_handler`。

### 3. api.ts — 新增 wrapper
- `zmodemStartUpload(sessionId, paths: string[]): Promise<void>`

### 4. TerminalPanel.tsx — 改触发逻辑
- `onZmodemStart(direction==="upload")`：弹文件选择器（`open({multiple:true})`），选完调 `zmodemStartUpload(sessionId, paths)`。不再初始化 bridge 的 upload。
- `onZmodemRaw`：upload 方向不再 `bridge.feed(data)`（Rust 自己消费）。download 方向不变。
- 进度/完成/结束事件监听**不变**（已订阅，payload 格式一致）。

### 5. zmodem-bridge.ts — 保留但降级
- `handleUpload` 路径保留不删（作为 fallback/未来可移除），但 TerminalPanel 不再调用它做 upload。

## 多文件流程（关键）
```
rz 启动 → 发 ZRINIT → Rust 检测到 → emit zmodem_start(upload) → mode=Zmodem, tx=None
  → 前端弹文件选择器 → 用户选 N 个文件 → 调 zmodemStartUpload(paths)
  → reader 打开文件1，创建 sender1，feed(缓存的ZRINIT) → sender 回 ZSINIT/ZFILE
  → rz 回 ZRPOS → sender.feed → 进入 SendingData → poll 循环发 ZDATA
  → 文件1 ZEOF → rz 回 ZRINIT → reader 从 tx_queue 取文件2，创建 sender2
  → ... 直到队列空 → 发 ZFIN → session_end
```

## 不需要改的
- 无新前端事件类型（progress/complete/end/error 已覆盖）
- 无新 abort/finish 路径（`ZmodemAbort`/`ZmodemFinish` 方向无关，已存在）
- `rz_open_read`/`rz_read_chunk` 不再需要（reader 直接 owns File），但保留不删
- zmodem.js 库不删（bridge download 路径不用，但保留）

## 风险控制
- passthrough 路径保留为 fallback：如果 ZRINIT 后前端没调 start_upload（比如旧前端），退回 zmodem.js
- ZmodemSender 已在 MCP 中验证握手+传输+多文件
- 改动集中在 ssh.rs reader loop，模式完全镜像已验证的下载路径
