# MCP ssh_exec 走 GUI tab + 自动启动 + 配置开关

## 目标
1. **自动启动**：MCP 调用时 GUI 没开 → MCP 自动拉起 myshell.exe，等 IPC 就绪
2. **同步展示**：AI 执行的 ssh_exec 命令**显示在 GUI 终端 tab 里**，用户实时可见，输出回传给 AI
3. **配置开关**：MCP 设置加"界面同步展示"开关，关闭时 ssh_exec 走原来的独立连接（不显示）

## 架构设计

### 核心流程（开关开启时）
```
AI 调 ssh_exec(connection, command)
  → MCP server 读 IPC 端口（没有 → 自动启动 GUI → 等就绪）
  → MCP 通过 IPC 发 {action:"exec_in_tab", connection_id, command, timeout}
  → GUI IPC listener 收到 → emit "mcp-gui-command" 事件
  → 前端 listener:
      1. 找/开该连接的终端 tab（复用 open_in_gui 的聚焦逻辑）
      2. 等连接就绪
      3. 发 sentinel 包裹的命令到 PTY: command + "\necho __MCP_DONE_<uuid>__:$?\n"
      4. 监听 ssh_output 事件流，累积输出
      5. 检测到 sentinel 行 → 截取 sentinel 之间的内容作为 stdout
      6. 解析 sentinel 末尾的 $? 作为 exit_code
      7. 通过 IPC 回传 {stdout, exit_code} 给 MCP
  → MCP 返回给 AI
```

### Sentinel 机制（解决"命令何时结束"问题）
当前 PTY 输出是无界流，没有命令边界。用 sentinel 标记法：
- 发送：`<command>\n` 然后 `echo __MCP_DONE_<uuid>__:$?\n`
- 捕获：累积 ssh_output 字节，正则匹配 `__MCP_DONE_<uuid>__:(\d+)`
- 输出 = sentinel 之前、命令之后的全部字节（剥掉 PTY 回显）
- exit_code = sentinel 里的数字
- 超时保护：超过 timeout 秒还没看到 sentinel → 返回已有输出 + 超时错误

### 自动启动 GUI
- MCP 读不到 `gui-ipc-port` 文件 → `Command::new(myshell_exe_path).spawn()`
- myshell_exe_path = MCP 自己的路径同目录的 myshell.exe（`E:\Program Files\MyShell\myshell.exe`）
- 轮询等待端口文件出现（最多 30 秒，每 1 秒检查）
- 就绪后继续正常 IPC 流程

### 配置开关
`<config_dir>/myshell/mcp-command-rules.json` 加字段 `show_in_gui: bool`（默认 true）。
- true：ssh_exec 走 GUI tab（上述流程）
- false：ssh_exec 走原来的独立连接（当前行为，headless）

## 实施步骤

### Step 1：IPC 协议扩展（main.rs + myshell-mcp.rs）
- IPC 新增 action `exec_in_tab`：请求 `{action, connection_id, command, timeout}`，响应 `{ok, stdout, exit_code, error?}`
- GUI listener（main.rs）：收到 exec_in_tab → 生成 uuid → emit 事件 `{action, connection_id, command, timeout, request_id}` → 等前端通过新 IPC 回写结果
- **新 IPC 命令 `mcp_exec_result`**：前端调这个 Tauri command 把结果写回给等待中的 listener（通过 oneshot channel 或共享 HashMap）

### Step 2：前端实现（App.tsx）
- listener 收到 `exec_in_tab` 事件：
  1. 找/开该连接的 tab（复用 open_in_gui 的 find-or-open 逻辑）
  2. 拿到 sessionId
  3. 通过新 API `sshSendRaw(sessionId, data)` 发命令 + sentinel（已有 ssh_send 可复用）
  4. 临时订阅 `onSshOutput(sessionId)`，累积字节直到 sentinel
  5. 调 `mcpExecResult(request_id, {stdout, exit_code})` 回传
- 命令确认规则仍然生效（在 GUI 侧检查 command_rules，需要确认时弹框）

### Step 3：MCP ssh_exec 改造（myshell-mcp.rs）
- 读 `show_in_gui` 配置
- true → 走 IPC exec_in_tab 流程（自动启动 GUI + 发命令 + 等结果）
- false → 走原来的独立连接（当前代码不动）
- 危险命令确认：show_in_gui=true 时在 GUI 侧检查规则弹框；false 时在 MCP 侧检查（当前行为）

### Step 4：配置 UI（SettingsPanel.tsx）
- MCP 设置加 toggle："ssh_exec 命令在界面终端同步展示（关闭则后台静默执行）"
- 保存到 mcp-command-rules.json 的 show_in_gui 字段

### Step 5：自动启动逻辑（myshell-mcp.rs）
- `ensure_gui_running()` 函数：读端口文件 → 没有则 spawn myshell.exe → 轮询等就绪
- 路径解析：`std::env::current_exe()` 同目录找 myshell.exe

## 复杂度评估
这是迄今最复杂的 MCP 功能——涉及双向 IPC（MCP→GUI 发命令，GUI→MCP 回结果）、PTY 输出流解析、自动进程启动。但每一步都有现成的积木可复用（IPC 桥、open_in_gui 的 tab 管理、ssh_send 的输入注入、ssh_output 的输出流）。

## 风险点
1. **Sentinel 可靠性**：极端情况下命令输出里可能碰巧包含 sentinel 字符串 → 用足够长的 uuid（32 字符）使碰撞概率为零
2. **PTY 回显**：命令本身会被 shell 回显到输出 → sentinel 匹配时需要跳过命令行本身的回显
3. **超时**：交互式命令（vim/top）不退出 → sentinel 永远不出现 → 靠 timeout 兜底
4. **多 tab 并发**：多个 AI 工具调用同时到达 → 每个 request_id 独立，各自有自己的 tab 或复用已有
