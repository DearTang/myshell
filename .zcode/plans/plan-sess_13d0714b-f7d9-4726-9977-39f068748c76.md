# MCP ssh_exec 改造方案：会话复用 + 原地重连 + 输出加固

## 问题总结

当前 MCP `ssh_exec`（show_in_gui 路径）有 5 个核心问题：
1. **慢**：每次无脑 `open_connection` + `sleep(5s)`，会话已存在也照等
2. **竞态**：open_connection 和 exec_in_tab 各触发一次连接，同服务器连两次
3. **会话超时不重连**：服务器 TMOUT 踢断后，MCP 下次命令开新 tab，旧的残留
4. **颜色丢失**：`App.tsx:532` 用 ansiCleaned 覆盖了带色 stdout
5. **输出炸弹**：outputBuf 无上限 + 全文正则 = O(n²)，大输出卡死浏览器

## 改造范围（4 个文件，Rust 零改动）

| 文件 | 改动 | 对应问题 |
|------|------|----------|
| `src-tauri/src/bin/myshell-mcp.rs` | 砍掉 exec_in_gui_tab 里的 open_connection + sleep(5s) | 问题 1、2 |
| `src/App.tsx` | exec_in_tab 三态查找（connected/disconnected/absent）+ 复用 reconnectOne；修复颜色覆盖 bug；outputBuf 上限 + 尾部正则 | 问题 2、3、4、5 |
| `src/App.tsx`（tab 生命周期） | 解耦 tab.id 与 sessionId：tab 用稳定 key，sessionId 独立字段 | 问题 3（保留历史） |
| `src/components/TerminalPanel.tsx` | sessionId 变化时不再销毁重建 xterm，改为切换数据源 | 问题 3（保留历史） |

## 模块 A：MCP 侧瘦身（myshell-mcp.rs）

### 改动：`exec_in_gui_tab` 函数（1161-1233 行）

**砍掉冗余的 open_connection + sleep(5s)**，因为前端的 exec_in_tab handler 本身就会处理"找不到 tab 就开/连、找得到就直接用"。

改前流程：
```
ensure_gui_running → send_gui_open_command → sleep(5s) → exec_in_tab
```
改后流程：
```
ensure_gui_running → exec_in_tab（前端自动复用或连接）
```

具体改动（1161-1233 行）：
- 删除 1180-1186 行的 `send_gui_open_command(...)` + `tokio::time::sleep(5s)`
- 保留 `ensure_gui_running()`（MCP 第一次调用时需要确保 GUI 在跑）
- 直接走 `exec_in_tab` IPC 调用
- `stream.set_read_timeout` 保持 `timeout + 15`（给前端连接 + 执行留余量）

**效果**：会话已存在时从 5-6s 降到 <1s；消除双连接竞态。

## 模块 B：前端连接状态机（App.tsx exec_in_tab handler）

### B1. exec_in_tab 三态查找（412-614 行）

当前逻辑只查 `status === "connected"`，找不到就开新 tab。改为三态：

```typescript
// 改前（418-420 行）：
const existing = tabsRef.current.find(
  (t) => t.connectionId === connection_id && t.type === "terminal" && t.status === "connected"
);

// 改后：分两步查找
// 第一步：找该 connection 的 terminal tab（不管 status）
const existingTab = tabsRef.current.find(
  (t) => t.connectionId === connection_id && t.type === "terminal"
);

// 第二步：根据状态分支
if (existingTab?.status === "connected" && existingTab.sessionId) {
  // 直接执行
  runExec(existingTab.sessionId);
} else if (existingTab && (existingTab.status === "disconnected" || existingTab.status === "error")) {
  // 原地重连：复用 reconnectOne，等它返回新 sessionId
  const ok = await reconnectOne(existingTab.id);
  if (ok) {
    // reconnectOne 已经更新了 tab 的 sessionId，从 tabsRef 读最新值
    const reconnected = tabsRef.current.find(t => t.id === /* 新 id 或原 id */);
    if (reconnected?.sessionId) runExec(reconnected.sessionId);
    else mcpExecResult(requestId, { ok: false, error: "重连后未找到会话" });
  } else {
    mcpExecResult(requestId, { ok: false, error: "重连失败：会话已断开且无法恢复" });
  }
} else {
  // 没有 tab → 开新 tab（原有 handleConnect + 轮询逻辑）
  handleConnect(config);
  // ... 轮询逻辑不变（589-614 行）
}
```

**注意**：reconnectOne 会改 tab.id（= 新 sessionId），轮询时要按 connectionId 而非 tab.id 查找。

### B2. 解耦 tab.id 与 sessionId（保留终端历史的关键）

**当前问题**：`tab.id === sessionId`，React key 用 `tab.id`（1147 行），重连改 sessionId → key 变 → xterm 销毁重建 → 历史丢失。

**改造**：让 tab 拥有独立的稳定 `id`（不随重连变化），`sessionId` 只是数据字段：

- **App.tsx**：
  - `handleConnect`（767-861 行）：tab 的 `id` 改为独立生成（如 `tab-${Date.now()}-${rand}`），不再等于 sessionId。`sessionId` 单独赋值。
  - `reconnectOne`（866-963 行）：**不再改 tab.id**，只更新 `tab.sessionId`。broadcastIds 用 tab.id，无需迁移。
  - exec_in_tab 轮询、handleCloseTab 等所有引用 `tab.id` 的地方：检查是否实际想用 sessionId（如 sshSend/sshDisconnect 用 sessionId，tab 管理用 id）。
  - `activeTabId` 语义不变（指向 tab.id）。

- **TerminalPanel.tsx**：
  - 主 mount effect 的依赖数组（665 行 `}, [sessionId]`）改为 `}, [tabId]`（或一个稳定标识），**不再因 sessionId 变化而销毁重建**。
  - 在 effect 内部监听 sessionId 变化（通过 ref 比较）：当 sessionId 变了，**不重建 xterm**，而是：解绑旧的 onSshOutput/onSshClosed → 用新 sessionId 重新订阅 → 写一行 `[Reconnected]` 提示。
  - `sshSend`/`sshResize` 调用要用最新的 sessionId（通过 ref）。

### B3. MCP exec 的保险库锁定快速失败

在 exec_in_tab handler 开头（handleConnect 之前），先检查保险库状态。如果 MCP 侧能感知到"保险库可能锁了"，直接报错而非等 30s 超时。

但更简单的做法：**前端 handleConnect 失败时会设 status="error"**，exec_in_tab 的 else 分支轮询时，如果发现 tab 变成 "error" 而非 "connected"，立刻报错给 MCP（不等 30s 轮询耗尽）：

```typescript
// 在轮询 checkInterval 里（598-613 行）增加 error 检查
const tab = tabsRef.current.find(t => /* 匹配 */);
if (tab?.status === "error") {
  clearInterval(checkInterval);
  mcpExecResult(requestId, { ok: false, error: `连接失败：${tab.errorMessage || "请检查保险库是否解锁"}` });
  return;
}
```

## 模块 C：输出捕获加固（App.tsx runExec）

### C1. 修复颜色丢失（449-545 行）

**根因**：`App.tsx:532-538` 用 `ansiCleaned`（无 ANSI 版）覆盖了 `stdout`，本意只是用它定位 sentinel 行的位置。

**修复**：ansiCleaned 只用于定位，不覆盖 stdout：

```typescript
// 改前（532-541 行）：
const ansiCleaned = stdout.replace(...);
const helperIdx = ansiCleaned.search(/echo __MCP_DONE_/);
if (helperIdx >= 0) {
  stdout = ansiCleaned.slice(0, ...);  // ← BUG：用无色版覆盖了！
} else {
  stdout = ansiCleaned;                 // ← BUG：同上
}

// 改后：用 ansiCleaned 定位，但截取原始 stdout
const ansiCleaned = stdout.replace(/\x1b\][0-9;]*.*?(?:\x07|\x1b\\)/g, "")
                          .replace(/\x1b\[[0-9;]*[a-zA-Z]/g, "");
const helperIdx = ansiCleaned.search(/echo __MCP_DONE_/);
if (helperIdx >= 0) {
  // 用 ansiCleaned 算出要删的行数，但在原始 stdout 上截断（保留颜色）
  const lineStart = ansiCleaned.lastIndexOf("\n", helperIdx);
  const cutPos = lineStart >= 0 ? lineStart : helperIdx;
  // 把 ansiCleaned 的位置映射回 stdout：由于两者只差 ANSI 码，
  // 找 ansiCleaned 第 cutPos 个可见字符在 stdout 中对应的字节位置
  stdout = stripFromAnsiPosition(stdout, cutPos);
}
// ANSI 清洗正则升级：\x1b][0-9]; → \x1b\]\d+; 兼容多位 OSC 参数（如 OSC 133）
```

需要新增一个辅助函数 `stripFromAnsiPosition`：按可见字符计数在带 ANSI 的字符串上定位截断点。

### C2. outputBuf 上限 + 尾部正则（461-480 行）

```typescript
// 改前：
outputBuf += decode(data);                    // 无上限
const match = outputBuf.match(sentinelRe);    // 全文正则 O(n)

// 改后：
outputBuf += decode(data);
if (outputBuf.length > 4 * 1024 * 1024) {     // 4MB 上限（对齐 headless 路径）
  outputBuf = outputBuf.slice(-4 * 1024 * 1024);
}
// 只检查尾部 2KB（sentinel 总在最后）
const tail = outputBuf.slice(-2048);
const match = tail.match(sentinelRe);
if (!match) return;
// 如果尾部匹配到了，再从完整 outputBuf 定位（match.index 需补偿 offset）
const fullMatchIndex = outputBuf.length - tail.length + match.index;
```

### C3. TerminalPanel sentinel filter 保持不变

`TerminalPanel.tsx:468-511` 的 render-layer filter 已经能正确隐藏 sentinel 行，本次不改。sentinel 机制保留（用户选择"优化 sentinel"方案）。

## 验证清单

改造完成后需验证的场景：

1. **速度**：会话已存在时连续发 3 条命令，每条应在 1s 内返回（之前 5-6s）
2. **竞态消除**：观察 GUI 不再出现重复 tab
3. **会话超时重连**：手动在服务器设 `TMOUT=10`，等 10s 后 MCP 发命令，应原地重连（保留历史，显示 [Reconnected]），不开新 tab
4. **颜色**：`ls --color` 命令，AI 收到的输出应保留 ANSI 色码（或转成语义标记），终端仍显示彩色
5. **大输出**：`seq 1 1000000` 命令，浏览器不卡死，outputBuf 被截断到 4MB
6. **保险库锁定**：锁保险库后 MCP 发命令，应快速报错（不等 30s）
7. **普通用户重连**：手动点 CommandBar 的"重连"按钮，xterm 历史保留，只重建连接

## 风险与缓解

| 风险 | 缓解 |
|------|------|
| tab.id 与 sessionId 解耦改动面大，可能遗漏引用 | 全局搜索 `tab.id` 和 `sessionId` 赋值点，逐一核对；先跑 `npx tsc --noEmit` |
| TerminalPanel 的 sessionId 变化处理复杂，可能引入内存泄漏 | 仔细管理 unlisten 函数；重连时确保旧监听器解绑 |
| stripFromAnsiPosition 函数可能有边界 case | 先实现简单版（按可见字符计数），用 `ls --color` 和复杂输出测试 |
| reconnectOne 改造影响广播级联逻辑 | 广播用 tab.id（现在稳定），反而更简单；级联逻辑测试 |

## 不做的事

- **OSC 133**：本次不改，sentinel 够用且风险低（用户选择）
- **cwd 恢复**：重连后是新 shell，cwd 回 home（用户接受）
- **Rust 侧改动**：零改动，重连 = disconnect + connect 前端透明处理
- **headless 路径**：不改（它是 fallback，且本身较健康）
