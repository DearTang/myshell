# Rust 端原生 ZMODEM 接收器（下载提速到 Xshell 水平）

## 问题根因

当前 ZMODEM 下载数据路径：`SSH → Rust emit(IPC①, JSON序列化) → JS consume → JS buffer → szWriteChunk(IPC②, JSON序列化) → Rust 写文件`。两次 IPC 跨界 + JSON 序列化（`Vec<u8>` → `[0,1,2,...]` 数字数组，2MB 膨胀成 ~8MB JSON）吃掉大部分带宽，上限 ~2.5MB/s。

## 方案：Rust 原生接收器

在 Rust 端实现完整的 ZMODEM 接收协议状态机。数据 `SSH → Rust 解析 → 直接写文件`，**零 IPC 跨界**。仅控制事件（文件 offer、进度、完成）跨 IPC。

### 方向判定（可靠）

ZMODEM 第一帧决定方向：
- 收到 **ZRQINIT**（typenum 0）→ 远端是 `sz` → **下载**，激活原生接收器
- 收到 **ZRINIT**（typenum 1）→ 远端是 `rz` → **上传**，回退 JS zmodem.js（上传路径性能可接受，暂不优化）

### 新建文件：`src-tauri/src/zmodem_rx.rs`（~350 行）

ZMODEM 接收器状态机，核心结构：

```rust
pub struct ZmodemReceiver {
    state: RxState,
    file: Option<std::fs::File>,
    bytes_written: u64,
    file_size: u64,
    current_filename: String,
    parse_buf: Vec<u8>,    // 跨 Data 块的帧拼接缓冲
}

enum RxState {
    Probing,           // 解析首帧判定方向
    WaitingZfile,      // 已发 ZRINIT，等 ZFILE
    WaitingAccept,     // 收到 ZFILE，等前端给路径
    Transferring,      // 写 ZDATA 到文件
    WaitingZeof,       // 等文件结束
    FileComplete,      // ZEOF 收到，等下一个 ZFILE 或 ZFIN
    Done,              // ZFIN 收到，等 OO
}
```

**CRC 策略：跳过 CRC 校验。** SSH/TCP 是可靠传输，ZMODEM CRC 是为不可靠串口设计的。跳过 CRC 简化实现并消除 CRC 实现 bug 风险。只解析帧结构定位数据边界。

**ZDLE 解码：** `0x18` 后面的字节 XOR `0x40`。

**输出动作**（`feed()` 返回）：
```rust
pub enum RxAction {
    Send(Vec<u8>),           // 发给远端的协议字节（ZRINIT/ZRPOS/ZACK/ZFIN...）
    EmitOffer { name: String, size: u64 },  // 通知前端有文件待下载
    Progress { written: u64, total: u64 },
    FileComplete,
    SessionEnd,
    Passthrough(Vec<u8>),    // 检测到上传，把已缓冲字节交回 JS
}
```

### 协议流程（下载路径）

```
我们                              lrzsz sz
  |                                  |
  |  ← ZRQINIT (你在吗?)             |
  |  ZRINIT (caps: CANFDX|CANOVIO|CANFC32 = 0x23) →  |
  |                                  |
  |  ← ZSINIT (可选)                  |
  |  ZACK →                          |
  |                                  |
  |  ← ZFILE (文件名+大小)            |
  |  [emit zmodem_offer → 前端弹目录选择] |
  |  [前端返回路径]                   |
  |  ZRPOS(offset=0) →               |
  |                                  |
  |  ← ZDATA + ZCRCG子包×N (firehose) |
  |  [直接写文件，零IPC]              |
  |  ← ZCRCE (最后一块)               |
  |                                  |
  |  ← ZEOF (文件结束)                |
  |  ZRINIT → (准备好接收下一个)      |
  |                                  |
  |  ← ZFIN (全部传完)                |
  |  ZFIN → (确认)                   |
  |  ← "OO" (Over and Out)           |
  |  [emit zmodem_end]               |
```

### 修改 `src-tauri/src/ssh.rs`（~100 行改动）

1. **新 SessionCommand 变体：**
   ```rust
   ZmodemAcceptOffer { path: Option<PathBuf> },  // None = skip
   ```

2. **channel_reader 改动：**
   - 添加 `zmodem_rx: Option<ZmodemReceiver>` 状态
   - 进入 Zmodem 模式时创建 receiver（Probing 状态），feed 初始字节
   - 若 receiver 返回 `Passthrough(bytes)`：发 zmodem_start(upload) + zmodem_raw(bytes)，切换到旧 passthrough 模式
   - 若 receiver 激活（下载）：Data 消息直接 feed 给 receiver，不再 emit zmodem_raw
   - 处理 receiver 返回的 actions：Send→channel.data()，EmitOffer→sink.emit，Progress→sink.emit，SessionEnd→emit zmodem_end
   - ZmodemAcceptOffer 命令：传给 receiver，触发 ZRPOS 发送

3. **handle_incoming_data 的 Zmodem 分支：**
   - 如果有 active receiver：feed 数据给 receiver，处理 actions
   - 如果 passthrough（上传）：保持现有 emit zmodem_raw 行为

### 修改 `src/zmodem-bridge.ts`（~100 行改动）

按方向分叉：

**下载（native）：**
- `zmodem_start { direction: "download" }` → 设置 `nativeDownload = true`，显示进度面板
- `zmodem_offer` → 弹目录选择（首次）或用缓存目录，调 `zmodemAcceptOffer(sessionId, path)`
- `zmodem_progress` → 更新 status（bytesTransferred 等）
- `zmodem_end` → reset
- **不创建 zmodem.js Session，不监听 zmodem_raw**

**上传（JS zmodem.js）：**
- `zmodem_start { direction: "upload" }` → 保持现有 zmodem.js 流程不变
- 监听 zmodem_raw，feed 给 zmodem.js

### 预期性能

| 路径 | IPC 次数（323MB文件） | 预期速度 |
|------|----------------------|---------|
| 旧 JS 路径 | ~40,000 emit + ~1,200 szWriteChunk | ~2.5 MB/s |
| **新 Rust 原生** | **0**（仅 ~20 次 offer/progress/end） | **10-50 MB/s**（受限于 SSH/磁盘） |

### 风险与回退

- **风险**：ZMODEM 协议解析 bug 导致文件损坏。缓解：跳过 CRC 但保留帧结构校验；ZEOF 时验证字节计数。
- **回退**：若原生接收器遇到无法解析的帧，emit error + 切回 Normal 模式（不影响终端）
- 上传路径完全不受影响（遇到问题只影响下载）
